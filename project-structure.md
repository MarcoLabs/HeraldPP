# Project Structure

This document describes where to find source files and how the UI-related code is organized.

## Top-level directories

```text
project/
├── include/     # C++ header files (.h)
├── src/         # C++ source files (.cpp)
└── ui/          # Slint UI files (.slint)
```

The `include/` and `src/` directories follow the same organizational structure: headers go in `include/`, and their implementations go in the corresponding location under `src/`.

## Full example layout

```text
project/
├── include/
│   ├── app/                         # Application logic (no Slint dependency)
│   │   └── MemoryGame.h
│   └── ui/                          # UI-related C++ headers
│       ├── MainWindowController.h
│       └── components/
│           └── MemoryGameController.h
│
├── src/
│   ├── main.cpp
│   ├── app/
│   │   └── MemoryGame.cpp
│   └── ui/                          # UI-related C++ implementations
│       ├── MainWindowController.cpp
│       └── components/
│           └── MemoryGameController.cpp
│
└── ui/                              # Slint UI definitions
    ├── MainWindow.slint
    ├── components/
    │   └── MemoryTile.slint
    └── pages/
        └── MemoryGame.slint
```

The names above are examples; the actual files and subdirectories depend on the project.

## What belongs where?

| Location | Contents |
|---|---|
| `include/` | C++ header files (`.h`) |
| `src/` | C++ implementation files (`.cpp`) |
| `ui/` | Slint UI files (`.slint`) |
| `include/app/`, `src/app/` | Application logic that does not depend on Slint |
| `include/ui/`, `src/ui/` | UI controllers and other C++ code that interacts directly with the UI |

## Code style

- Tabs for indentation, no unnecessary comments.
- Opening braces go on their own line, in both C++ and Slint.
- File names match the class or component they implement: `MemoryGame.h`, `MemoryGame.cpp`, `MemoryGame.slint`. Files that are not a class, such as `main.cpp`, are the exception.
- Functions and methods use `PascalCase`, except getters, which are `getX`.
- Variables and fields use `camelCase`; member variables keep the `m_` prefix.
- Use `size_t`, not `std::size_t`.
- Use `i++` where pre/post increment makes no difference.
- Negated conditions are written `if (! condition)`.
- Structs without a constructor initialize every field: `std::string symbol{};`.
- Constructors keep the signature and initializer list on one line: `Class::Class(args): a(), b() { }`.
- Headers use the `.h` extension.

Names generated by Slint (`set_tiles`, `on_tile_clicked`, `face_up`, ...) keep their generated form.

## UI architecture

Keep the visual structure and C++ UI integration separate:

- **`ui/`** defines the visual components, layout, styling, and UI-side interactions.
- **`include/ui/` and `src/ui/`** contain C++ UI controllers. Controllers register Slint callbacks, translate UI events into application operations, and update the displayed state.
- **`include/` and `src/` outside `ui/`** contain application logic that should not depend on Slint.

A controller does not need to mirror the Slint component hierarchy. Organize controllers around logical responsibilities instead. A controller may coordinate multiple Slint components, and small interactions can remain entirely inside Slint.

### Which components are visible to C++?

Slint only generates C++ classes for components exported from the entry file (`ui/MainWindow.slint`). Components nested inside the window, such as the memory game page, are not reachable from C++ directly. Instead, the window exposes the properties and callbacks that C++ needs and forwards them to the nested components. Structs used by those properties (such as `TileData`) must also be re-exported from `MainWindow.slint`.

The header generated from `ui/MainWindow.slint` is included as `"MainWindow.h"`. Because only the entry file generates a header, the Slint `MemoryGame` page and the C++ `app::MemoryGame` class do not clash.

## Startup and initialization

Keep `src/main.cpp` focused on application startup:

1. Create the main Slint window.
2. Initialize the application logic and its state.
3. Construct the UI controllers and register their callbacks.
4. Start the Slint event loop.

Keep controllers alive for as long as their registered callbacks may be invoked. For example, controllers created as local variables in `main()` remain alive while `mainWindow->run()` is executing.

The application logic must be initialized before the controllers are constructed, because a controller fills the Slint model from the current game state in its constructor.

## Example: Memory game

The following example shows every layer of a small memory game, from application logic to the Slint UI.

### Application logic

The game logic knows nothing about Slint. It stores the tiles, tracks the current selection, and exposes simple operations.

**`include/app/MemoryGame.h`**

```cpp
#pragma once

#include <cstddef>
#include <optional>
#include <string>
#include <utility>
#include <vector>

namespace app
{

struct Tile
{
	std::string symbol{};
	bool faceUp{false};
	bool matched{false};
};

class MemoryGame
{
public:
	explicit MemoryGame(size_t pairCount = 8);

	void Initialize();
	void RevealTile(size_t index);
	void HideMismatched();

	bool HasPendingMismatch() const;
	bool IsWon() const;
	int getMoves() const;
	const std::vector<Tile>& getTiles() const;

private:
	size_t m_pairCount;
	std::vector<Tile> m_tiles;
	std::optional<size_t> m_first;
	std::optional<std::pair<size_t, size_t>> m_mismatch;
	size_t m_matchedPairs{0};
	int m_moves{0};
};

}
```

**`src/app/MemoryGame.cpp`**

```cpp
#include "app/MemoryGame.h"

#include <algorithm>
#include <random>

namespace app
{

MemoryGame::MemoryGame(size_t pairCount): m_pairCount(pairCount) { }

void MemoryGame::Initialize()
{
	m_tiles.clear();
	for (size_t i = 0; i < m_pairCount; i++)
	{
		std::string symbol(1, static_cast<char>('A' + i));
		m_tiles.push_back({symbol});
		m_tiles.push_back({symbol});
	}

	std::mt19937 rng{std::random_device{}()};
	std::shuffle(m_tiles.begin(), m_tiles.end(), rng);

	m_first.reset();
	m_mismatch.reset();
	m_matchedPairs = 0;
	m_moves = 0;
}

void MemoryGame::RevealTile(size_t index)
{
	if (index >= m_tiles.size() || m_mismatch)
	{
		return;
	}

	Tile& tile = m_tiles[index];
	if (tile.faceUp || tile.matched)
	{
		return;
	}

	tile.faceUp = true;

	if (! m_first)
	{
		m_first = index;
		return;
	}

	m_moves++;
	size_t first = *m_first;
	m_first.reset();

	if (m_tiles[first].symbol == tile.symbol)
	{
		m_tiles[first].matched = true;
		tile.matched = true;
		m_matchedPairs++;
	}
	else
	{
		m_mismatch = std::make_pair(first, index);
	}
}

void MemoryGame::HideMismatched()
{
	if (! m_mismatch)
	{
		return;
	}

	m_tiles[m_mismatch->first].faceUp = false;
	m_tiles[m_mismatch->second].faceUp = false;
	m_mismatch.reset();
}

bool MemoryGame::HasPendingMismatch() const
{
	return m_mismatch.has_value();
}

bool MemoryGame::IsWon() const
{
	return m_matchedPairs == m_pairCount;
}

int MemoryGame::getMoves() const
{
	return m_moves;
}

const std::vector<Tile>& MemoryGame::getTiles() const
{
	return m_tiles;
}

}
```

While a mismatch is pending, further `RevealTile()` calls are ignored. The UI layer decides when to call `HideMismatched()` (after a short delay), which keeps timing out of the game logic.

### UI controller

A controller owns the C++ side of a UI component: it keeps a handle to the Slint window, receives a reference to the application logic, and registers callbacks during construction.

**`include/ui/components/MemoryGameController.h`**

```cpp
#pragma once

#include "MainWindow.h"
#include "app/MemoryGame.h"

#include <memory>

class MemoryGameController
{
public:
	MemoryGameController(slint::ComponentHandle<MainWindow> window, app::MemoryGame& game);

private:
	slint::ComponentHandle<MainWindow> m_window;
	app::MemoryGame& m_game;
	std::shared_ptr<slint::VectorModel<TileData>> m_tiles;

	void OnTileClicked(int index);
	void OnRestartClicked();
	void Refresh();
};
```

**`src/ui/components/MemoryGameController.cpp`**

```cpp
#include "ui/components/MemoryGameController.h"

#include <chrono>
#include <utility>

MemoryGameController::MemoryGameController(slint::ComponentHandle<MainWindow> window, app::MemoryGame& game): m_window(std::move(window)), m_game(game), m_tiles(std::make_shared<slint::VectorModel<TileData>>())
{
	m_window->set_tiles(m_tiles);
	m_window->on_tile_clicked([this](int index)
	{
		OnTileClicked(index);
	});
	m_window->on_restart_clicked([this]
	{
		OnRestartClicked();
	});

	Refresh();
}

void MemoryGameController::OnTileClicked(int index)
{
	m_game.RevealTile(static_cast<size_t>(index));
	Refresh();

	if (m_game.HasPendingMismatch())
	{
		slint::Timer::single_shot(std::chrono::milliseconds(800), [this]
		{
			m_game.HideMismatched();
			Refresh();
		});
	}
}

void MemoryGameController::OnRestartClicked()
{
	m_game.Initialize();
	Refresh();
}

void MemoryGameController::Refresh()
{
	const auto& tiles = m_game.getTiles();

	while (m_tiles->row_count() > tiles.size())
	{
		m_tiles->erase(m_tiles->row_count() - 1);
	}

	for (size_t i = 0; i < tiles.size(); i++)
	{
		TileData data{slint::SharedString(tiles[i].symbol), tiles[i].faceUp, tiles[i].matched};

		if (i < m_tiles->row_count())
		{
			m_tiles->set_row_data(i, data);
		}
		else
		{
			m_tiles->push_back(data);
		}
	}

	m_window->set_moves(m_game.getMoves());
	m_window->set_won(m_game.IsWon());
}
```

The model starts empty; the `Refresh()` call at the end of the constructor is what fills it from the game state, so the board is populated before the window is shown. Since the window holds the same `shared_ptr`, every later change is picked up by Slint automatically.

`TileData` is generated from the Slint struct in `MemoryTile.slint`, so its fields are `symbol`, `face_up`, and `matched` (Slint's `face-up` becomes `face_up` in C++).

The timer callback captures `this`, so the controller must outlive any pending timer. A local controller in `main()` satisfies this.

### Main window controller

When there is only one page, the main window controller can just own the page controller. As the app grows, it can also own other controllers and handle window-level concerns.

**`include/ui/MainWindowController.h`**

```cpp
#pragma once

#include "MainWindow.h"
#include "app/MemoryGame.h"
#include "ui/components/MemoryGameController.h"

class MainWindowController
{
public:
	MainWindowController(slint::ComponentHandle<MainWindow> window, app::MemoryGame& game);

private:
	MemoryGameController m_memoryGame;
};
```

**`src/ui/MainWindowController.cpp`**

```cpp
#include "ui/MainWindowController.h"

#include <utility>

MainWindowController::MainWindowController(slint::ComponentHandle<MainWindow> window, app::MemoryGame& game): m_memoryGame(std::move(window), game) { }
```

### Entry point

Construct controllers after creating the Slint window and before starting the event loop.

**`src/main.cpp`**

```cpp
#include "MainWindow.h"
#include "app/MemoryGame.h"
#include "ui/MainWindowController.h"

int main()
{
	auto mainWindow = MainWindow::create();

	app::MemoryGame game;
	game.Initialize();

	MainWindowController controller(mainWindow, game);

	return mainWindow->run();
}
```

The controller must remain alive while its callbacks can be invoked. A local controller in `main()` satisfies this because `run()` blocks until the event loop exits.

If a controller is a member of another controller, declare its dependencies before it in the class so they are initialized first. Also ensure that callbacks cannot outlive the controller they capture through `this`.

### Slint files

**`ui/components/MemoryTile.slint`**

```slint
export struct TileData
{
	symbol: string,
	face-up: bool,
	matched: bool,
}

export component MemoryTile inherits Rectangle
{
	in property <TileData> data;
	callback clicked();

	width: 64px;
	height: 64px;
	border-radius: 8px;
	background: data.matched ? #2e7d32 : data.face-up ? #fafafa : #1565c0;

	Text
	{
		text: data.face-up || data.matched ? data.symbol : "";
		font-size: 28px;
		color: data.matched ? #ffffff : #212121;
	}

	TouchArea
	{
		clicked =>
		{
			root.clicked();
		}
	}
}
```

**`ui/pages/MemoryGame.slint`**

```slint
import { Button } from "std-widgets.slint";
import { MemoryTile, TileData } from "../components/MemoryTile.slint";

export component MemoryGame inherits Rectangle
{
	in property <[TileData]> tiles;
	in property <int> moves;
	in property <bool> won;
	callback tile-clicked(int);
	callback restart-clicked();

	VerticalLayout
	{
		alignment: center;
		spacing: 12px;
		padding: 16px;

		Text
		{
			text: won ? "You won in \{moves} moves!" : "Moves: \{moves}";
			horizontal-alignment: center;
			font-size: 20px;
		}

		HorizontalLayout
		{
			alignment: center;

			GridLayout
			{
				spacing: 8px;

				for tile[i] in tiles: MemoryTile
				{
					row: Math.floor(i / 4);
					col: Math.mod(i, 4);
					data: tile;
					clicked =>
					{
						root.tile-clicked(i);
					}
				}
			}
		}

		Button
		{
			text: "Restart";
			clicked =>
			{
				root.restart-clicked();
			}
		}
	}
}
```

**`ui/MainWindow.slint`**

```slint
import { TileData } from "components/MemoryTile.slint";
import { MemoryGame } from "pages/MemoryGame.slint";

export { TileData }

export component MainWindow inherits Window
{
	title: "Memory Game";
	preferred-width: 400px;
	preferred-height: 480px;

	in property <[TileData]> tiles;
	in property <int> moves;
	in property <bool> won;
	callback tile-clicked(int);
	callback restart-clicked();

	MemoryGame
	{
		tiles: root.tiles;
		moves: root.moves;
		won: root.won;
		tile-clicked(index) =>
		{
			root.tile-clicked(index);
		}
		restart-clicked =>
		{
			root.restart-clicked();
		}
	}
}
```

The page handles layout and tile rendering entirely in Slint. Only the two events that change application state (`tile-clicked` and `restart-clicked`) are forwarded to C++.
